## 一、结论摘要

1. **融合方式已定并已落地**：秒哒不并入 AI助手 代码，而是以它本来的形态——**stdio MCP 服务**——被 AI助手 通过新增的 **stdio MCP 桥**统一托管调用。AI助手 保持单一主框架，秒哒成为"可插拔能力"。
2. **v2.3.0 已交付三项硬能力**：① stdio MCP 桥（后端 spawn 子进程 + HTTP 端点暴露，纯标准库）；② 讯飞星火**双通道**（OpenAI 兼容 `spark` 预设 + 原生 WebSocket `iflytek` 适配器）；③ 本地 **Skill 安装**（`/api/skills` + `@install` 命令 + 启动自动扫描）。
3. **实测结论**：秒哒自测 37/37；桥端到端 5/5（8 工具、plan/generate/qa 全通）；AI助手 源码冒烟 18/18；**打包产物冒烟 16/16**（EXE 24.86 MB，`mcp_stdio` 已冻结进包、`iflytek.js` 已打进包）。
4. **离"真正的 agent"还差一层内核**：当前 `runAgent` 已是工具调用循环，但缺计划-执行-校验、上下文压缩、模型能力探测、失败恢复与人机确认。这是 v3.0 的主体工作，本文件给出设计与里程碑。

## 四、v2.3.0 已交付（含实测）

### 4.1 stdio MCP 桥

新增 `src/v2.2.0-wip/mcp_stdio.py`（288 行，纯标准库）。

| 组件 | 职责 |
|---|---|
| `StdioServer` | 托管单个子进程：按需 spawn、自动 `initialize`、行式 JSON-RPC 往返、per-server 串行锁、崩溃隔离与 `restart_on_fail` |
| `StdioMCPManager` | 多 server 注册表（`id` / `name` 双索引），配置热替换 |
| `load_from_config()` | 启动时读 `mcpServers` 中 `transport === 'stdio-bridge'` 的条目（兼容旧 `mcpStdio` 数组） |
| `handle_mcp_stdio()` | 三个 HTTP 端点 |

端点：

```
GET  /api/mcp/stdio/servers            已托管 server 清单
POST /api/mcp/stdio/list?server=<id>   列出该 server 的工具
POST /api/mcp/stdio/call?server=<id>   body {name, arguments} → 文本结果
```

设计要点与安全边界：

- **命令只来自本地 config**，前端无法传入 command，杜绝任意命令执行；
- 环境变量按白名单注入（仅 `isidentifier()` 的键），不向前端回显；
- 子进程退出时收集 stderr 尾部用于排错，返回结构化错误；
- 忽略无 `id` 的 notification，避免协议噪声打断请求；
- 冻结兼容：函数级延迟导入 + `build.spec` 显式 `hiddenimports: ['mcp_stdio']`。

配置示例（写入 `config.json`）：

```json
{
  "mcpServers": [
    {
      "id": "forge",
      "name": "秒哒(local-app-forge)",
      "transport": "stdio-bridge",
      "command": "python",
      "args": ["D:\\AI\\开发工程\\软件开发工程\\workbuddy复刻秒哒MPC\\src\\server.py"],
      "cwd": "D:\\AI\\开发工程\\软件开发工程\\workbuddy复刻秒哒MPC",
      "restart_on_fail": true
    }
  ]
}
```

> **联调发现的真实缺陷（已修复）**：`_handle_mcp_stdio` 最初用含查询串的 `self.path` 直接切片，
> `list?server=forge` 被当成一个整段，永远命中不了 `list`，返回"未知 stdio MCP 操作"。
> 早期单测直接把预切好的数组喂给底层函数，绕过了这段解析，所以一直是"绿"的；
> **是打包产物的端到端测试第一次把它打出来**。修法：先 `urlparse(self.path).path` 再切片；
> 同时把单测改为走 `SafeHandler._handle_mcp_stdio` 真实路由，形成回归。教训写在这里：
> 单元测试绕过解析层＝假绿。

前端 `agent.js` 同步新增 `transport === 'stdio-bridge'` 分支，工具清单与调用统一走上述端点；MCP 添加表单支持"HTTP / Streamable / stdio 桥"三选一，stdio 模式下填命令与参数。

### 4.2 讯飞星火双通道

| 通道 | provider id | 端点 | 鉴权 | 函数调用 |
|---|---|---|---|---|
| OpenAI 兼容 | `spark` | `https://spark-api-open.xf-yun.com/v1` | 仅 APIKey | ✅ 支持 |
| 原生 WebSocket | `iflytek` | `wss://spark-api.xf-yun.com/v3.1/chat` | APPID + APIKey + APISecret | ❌ 不支持 |

原生适配器 `webdist/js/providers/iflytek.js`（168 行）：

- 纯 JS 实现 SHA-256 + HMAC-SHA256（不依赖 `crypto.subtle`，兼容任意上下文）；
- 按讯飞规范拼 `authorization` 串（`host / date / request-line` 三元签名）；
- 模型名 → domain 映射：`4.0Ultra` / `pro-128k` / `generalv3.1` / `generalv3` / `generalv3.5`；
- 流式增量回调 `onDelta(delta, full)`，终态 `status === 2` 收束；
- 返回结构与 `postChatStream` 对齐（`{role, content, tool_calls}`）。

**已知限制（必须在选型时告知用户）**：原生 WS 通道没有 `tools` 参数，**不能函数调用**，因此不能驱动工具/agent 循环；需要"讯飞 + 工具"时请选 `spark` 预设。原生通道的价值在于：指定 domain、走私有化/专线、以及 OpenAI 兼容网关不可用时的备用路径。

## 五、v3.0 目标架构

```
┌────────────────────────────────────────────────────────────┐
│ Shell        pywebview 窗口 / 浏览器回退（127.0.0.1 随机端口）│
├────────────────────────────────────────────────────────────┤
│ UI           React UMD 零构建 · @命令 · 设置 · MCP/Skill 面板 │
├────────────────────────────────────────────────────────────┤
│ Agent Core   规划 → 工具选择 → 执行 → 观察 → 校验 → 收敛      │
│              上下文压缩 · 会话持久化 · 失败恢复 · 人机确认     │
├────────────────────────────────────────────────────────────┤
│ Capability   本地工具 · Office 六件套 · Skill Runtime         │
│              MCP Hub（HTTP/SSE/stdio）· Forge Bridge          │
├────────────────────────────────────────────────────────────┤
│ Model        Provider Registry                                │
│              OpenAI 兼容层（主力）+ 原生适配器（spark/私有化）  │
│              能力探测 · 路由 · 降级 · 用量与成本               │
├────────────────────────────────────────────────────────────┤
│ Storage      config.json（本地）· app_data/skills/            │
│              sessions/ · audit/（哈希链）· snapshots/          │
└────────────────────────────────────────────────────────────┘
```

设计原则：

1. **模型层可换、工具层可插、内核层稳定**——三者解耦，换模型不改工具，加工具不改内核。
2. **一切能力都要能被"能力探测"**：模型是否支持 tools/流式/长上下文，运行时探测并自动降级（不支持 tools 时退化为"文本协议 + 解析"模式）。
3. **默认零出域**：不主动联网；联网必须由工具或用户显式触发，并计入零出域计数器（移植秒哒机制）。
4. **破坏性操作必须二次确认**：删除、覆盖、发布、外发邮件等，一律人机确认。

### 6.2 接入规范（v3.0 固化）

```js
// Provider 描述符（唯一扩展点，新增厂商不改内核）
{
  id: 'spark',
  label: '讯飞星火（OpenAI 兼容）',
  baseUrl: 'https://spark-api-open.xf-yun.com/v1',
  models: ['generalv3.5', '4.0Ultra', 'pro-128k'],
  defaultModel: 'generalv3.5',
  authMode: 'bearer',            // bearer | header | query-sign
  caps: { tools: true, stream: true, vision: false },
  adapter: null                   // 非 OpenAI 协议时填适配器名
}
```

规则：

- **优先 OpenAI 兼容**（占国内厂商 90% 场景），只有不兼容或需私有化时才写原生适配器；
- 适配器接口固定：`(cfg, sys, messages, onDelta) → {role, content, tool_calls}`，与 `postChatStream` 同构；
- **能力探测**：首次调用失败于 `tools` 参数时，自动以"无工具模式"重试一次并记录 `caps.tools=false`，不反复踩同一坑；
- **降级链**：主模型失败（429/超时/5xx）→ 备用模型（同厂商轻量档）→ 本地 Ollama → 明确报错，不静默失败；
- **密钥只存本地** `config.json`，不上传、不进日志；v3.0 计划改用 Windows DPAPI 加密存储。

讯飞原生通道的配置字段（设置面板已加）：`iflytekAppId` / `iflytekApiKey` / `iflytekApiSecret` / `iflytekDomain`（可选）/ `iflytekPath`（可选，默认 `/v3.1/chat`）。

## 七、Skill 机制设计（v3.0）

目标：从"内联 JS 技能"升级为"可安装、可授权、可分发"的技能生态。

### 7.1 目录与清单

```
app_data/skills/
  <skill-id>/
    SKILL.md          # 元信息 + 使用说明（人读，模型可读）
    manifest.json     # 机器读：id/label/version/entry/permissions/inputs
    main.js           # 入口（沙箱内执行）
```

```json
{
  "id": "docx_export",
  "label": "Word 导出",
  "version": "1.0.0",
  "entry": "main.js",
  "permissions": ["fs:write", "net:none"],
  "inputs": { "content": "string", "path": "string" },
  "runtime": "js"
}
```

### 7.2 权限与安全

| 权限 | 含义 | 默认 |
|---|---|---|
| `fs:read` / `fs:write` | 读写指定目录 | 拒绝，需声明 + 用户首次确认 |
| `net:none` | 禁止联网（默认值） | 强制 |
| `net:allow` | 允许联网 | 需显式声明 + 二次确认 |
| `exec` | 调用本地进程 | v3.0 不开放 |

安装流程：`@install <path>` → 校验 manifest → 展示权限清单 → 用户确认 → 落盘 → 注册。第三方技能默认 `net:none`。

### 7.3 与秒哒的关系

秒哒**不做成 skill**，保持 MCP 形态（它是长驻服务，不适合按次调用）。但秒哒的"六门质检"移植为 AI助手 的**产物质检门**：任何生成类技能（文档/表格/网页）产出后自动过门（结构完整性、可打开性、零出域、内容非空、路径合法、体积异常），不过门不交付。

## 八、MCP Hub 设计（v3.0）

三通道统一管理：

| 通道 | 传输 | 典型用途 | 状态 |
|---|---|---|---|
| HTTP | `POST /mcp`，JSON-RPC | 远程 MCP 服务 | ✅ 已有 |
| SSE / Streamable | `text/event-stream` | 远程流式 MCP | ⏳ 部分 |
| stdio 桥 | 子进程 stdin/stdout | 本地工具（秒哒等） | ✅ v2.3.0 |

v3.0 补齐：

- **健康检查**：定期 `tools/list` 探活，失败标红并可一键重启；
- **工具级开关**：单个 MCP 的单个工具可禁用（避免污染工具池、节省 token）；
- **工具命名空间**：`<server>.<tool>` 统一前缀，避免重名；
- **信任与审计**：首次接入记录来源与命令哈希，变更需重新确认。

## 九、Agent 内核设计（v3.0 主体）

### 9.1 主循环

```
用户输入
  → 意图判定（闲聊 / 问答 / 任务）
  → 计划（任务型：拆 1..N 步，产出可校验的步骤清单）
  → 循环（上限 N 步）：
       选工具 → 执行 → 观察结果 → 校验（是否达成该步目标）
       失败 → 重试（换参数/换工具，最多 2 次）→ 仍失败则降级或求助用户
  → 汇总（产物 + 依据 + 未决项）
```

### 9.2 关键机制

| 机制 | 现状 | v3.0 要求 |
|---|---|---|
| 工具调用循环 | ✅ 已有 | 增加步数上限与死循环检测 |
| 结果截断 | ❌ | 单工具结果超限截断并摘要，防上下文爆掉 |
| 上下文压缩 | ❌ | 超阈值时保留系统提示 + 最近 K 轮 + 任务摘要 |
| 会话持久化 | 部分（远程同步 messages） | 本地 `sessions/` 落盘，可恢复、可导出 |
| 人机确认 | ❌ | 破坏性操作前中断并请求确认 |
| 审计链 | ❌ | 每次工具调用记录哈希链（移植秒哒） |
| 快照回滚 | ❌ | 文件类产物改动前自动快照（移植秒哒） |
| 多模型路由 | ❌ | 按任务类型选模型（长文→Kimi，推理→DeepSeek-R，工具→GLM/Qwen） |

### 9.3 "真正的 agent"验收标准

1. 给一句自然语言任务，能自主拆步、选工具、执行、校验、交付，中途无需人工喂指令；
2. 工具失败能自行换路（换参数/换工具），连续失败才停；
3. 产出物可追溯：每一步用了什么工具、参数是什么、结果摘要；
4. 破坏性动作前必停，等人确认；
5. 断网时明确降级（本地模型或本地规则），不假装成功。

## 十一、风险与回滚

| 风险 | 影响 | 对策 |
|---|---|---|
| 原生 WS 讯飞无 tools | 选了该通道就用不了工具 | 设置面板明示；需要工具时引导选 `spark` |
| stdio 子进程继承全量环境变量 | 敏感变量可能被子进程读取 | 现状已按白名单"注入"，但仍是 `os.environ.copy()`；M3 改为最小环境启动 |
| 前端持有 API Key | 页面被注入即可窃取 | 仅本机 127.0.0.1 + CSP；M4 改 DPAPI，前端不落明文 |
| 模型幻觉触发错误工具 | 误操作文件 | 破坏性操作二次确认 + 快照回滚兜底 |
| stdio 子进程僵尸 | 端口/句柄泄漏 | 管理器统一 stop；退出时清理；`restart_on_fail` |
| 打包漏收模块 | EXE 功能缺失 | `smoke_exe.py` 固定验证 mcp_stdio/skills/provider 三处 |
| 涉密内容外流 | 合规风险 | 默认零出域；本地 Ollama 全离线；导出前脱敏检查 |

回滚方案：

- `builds/AI.Super-Agent_v2.2.0.exe` 完整保留，直接替换即可回到融合前；
- 源码级：`mcp_stdio.py` 为独立新增文件，删除并在 `launcher.py` 移除三处路由即恢复；
- 配置级：删除 `config.json` 中 `transport: "stdio-bridge"` 条目，桥即不再装载（不影响模型与其他工具）。
